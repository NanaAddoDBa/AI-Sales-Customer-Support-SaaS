# Identity and tenant context

Date: 2026-10-20. Status: implemented for P02; guarded Windows runtime restart remains blocked.

Use Supabase Auth for account verification, password sessions and recovery. Verify every incoming bearer token through getUser, then correlate its verified subject/session_id with current auth.sessions and a confirmed, non-anonymous, non-banned account in Postgres. A signed token alone does not authorize organization access. Read member role/revocation from current tenancy rows; user_metadata and client organization fields are not authority.

The API pool logs in as sales_api and fails startup if that role is privileged or unexpected. TenantDatabase scopes claims to a transaction with set_config(..., true), validates a live session and resets transaction context on commit/rollback. The worker role sales_worker has neither RLS bypass nor Auth/credential-table access. Its tenant scope comes from an opaque leased job token issued by the database, not a tenant value in the job payload. Claiming uses FOR UPDATE SKIP LOCKED; leases expire and completed leases stop authorizing reads. This phase provides the job boundary, not business job handlers.

Business schemas are unexposed to the Data API. All business tables have forced RLS and explicit grants. A small private SECURITY DEFINER surface avoids recursive membership RLS and checks Auth sessions without granting application logins Auth table access. It has an empty search_path, qualified objects, no PUBLIC execute and role-specific grants. Private object paths are tenant-prefixed; the knowledge bucket is not public. Composite foreign keys prevent cross-tenant customer/conversation/message and source/chunk relationships.

Accounts and roles are merchant permissions; they do not grant SaaS-operator access. Owner transfer/removal is unavailable in this phase. Admins cannot grant admin or modify owners/admins. Recent sign-in is required for member changes, credential access and password changes. Invitations store token hashes, expire and bind to verified email. Merchant owners/admins receive a token for manual sharing; no external invitation message is sent automatically.

Credential encryption uses AES-256-GCM, fresh 96-bit nonces and context binding to version, key ID, organization, connection and provider. Keys remain server-side; ciphertext alone is stored in Postgres. Rotation retains old keys for current/backup data and reencrypts in a locked transaction. No provider adapter or credential HTTP endpoint is activated by this groundwork.
